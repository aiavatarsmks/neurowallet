# DECISION: TON-деривация, совместимая с Tonkeeper

> Статус: **ПЛАН, ждёт одобрения Максима.** Код деривации/импорта не менялся.
> Это breaking change для хранения ключей: реализация только после явного «да»
> по разделу «Что нужно решить».

## TL;DR

- Сейчас TON-ключ получается из **12-словной BIP39-фразы** через SLIP-0010
  `m/44'/607'/0'/0'`. Tonkeeper использует **собственный алгоритм TON-мнемоники
  (24 слова)**, поэтому нашу фразу он либо не примет, либо получит другой ключ и
  другой адрес. TON-средства в других кошельках не восстанавливаются.
- Предложение: новые кошельки создаются с **24-словной фразой, валидной
  одновременно как BIP39 и как TON-мнемоника**. TON-ключ выводится по стандарту
  TON (как в Tonkeeper), остальные сети — как сейчас, по BIP39. Одна фраза
  восстанавливает всё: TON в Tonkeeper, ETH/USDT в MetaMask, SOL в Phantom и т.д.
- Проверено: такая фраза находится перебором в среднем за ~300 попыток,
  ~140 мс в Node (`bip39.generateMnemonic(256)` + `mnemonicValidate` из `@ton/crypto`).
- Существующие кошельки (все 12-словные) **нельзя сделать совместимыми с
  Tonkeeper пере-деривацией**: 12-словная фраза не является TON-мнемоникой.
  Для них нужна миграция на новый кошелёк с переводом средств, либо сознательное
  «оставить как есть».

## Как сейчас (факты из кода)

| Что | Где | Значение |
|---|---|---|
| Фраза | `lib/crypto/wallet.ts` `generateMnemonic()` | BIP39, 128 бит → **12 слов**; импорт в `pages/onboarding.tsx` требует ровно 12 |
| Seed | `wallet.ts` `importWalletFromMnemonic()` | `bip39.mnemonicToSeed(phrase)` (PBKDF2-HMAC-SHA512, salt `"mnemonic"`, 2048 итераций) |
| TON-ключ | `wallet.ts:85-86` | SLIP-0010 ed25519, `m/44'/607'/0'/0'` (все сегменты hardened) |
| Контракт | `lib/crypto/ton-tx.ts` | `WalletContractV4` (V4R2), workchain 0 |
| Показ адреса | `ton-tx.ts` `tonAddressFromPrivKey` | bounceable `EQ…` |
| Хранение | localStorage | `wallet_ton_address`, `wallet_ton_enc` (AES-GCM + PBKDF2) |

История: до 2026-06-27 TON выводился по non-hardened `m/44'/607'/0'/0/0`
(см. `LEGACY_DERIVATION_JUNE_USERS.md`, решено «accept + document»).

## Почему Tonkeeper не восстанавливает кошелёк

TON-стандарт (`@ton/crypto`, им пользуются Tonkeeper, Tonhub, MyTonWallet)
устроен иначе, чем BIP39 + SLIP-0010:

1. **Формат фразы.** TON-мнемоника — 24 слова из того же английского словаря
   BIP39, но с собственной проверкой: `entropy = HMAC-SHA512(key = фраза,
   data = пароль "")`, и фраза валидна, только если первый байт
   `PBKDF2(entropy, "TON seed version", 390 итераций)` равен 0. Контрольная сумма
   BIP39 при этом не используется. Наша 12-словная фраза отсекается уже по длине.
2. **Ключ.** `seed = PBKDF2-SHA512(entropy, salt "TON default seed",
   100 000 итераций)[0..32]` → ed25519. Никаких путей деривации (`m/44'/607'…`)
   нет. Значит, даже при одинаковых словах наш SLIP-0010-ключ и ключ Tonkeeper
   **разные**, и адреса тоже разные.
3. **Мелочь.** Мы показываем bounceable `EQ…`. Для кошельков, особенно ещё не
   развёрнутых, принят non-bounceable `UQ…`. Адрес тот же, но пользователи и
   биржи ждут `UQ…`.

Итог: средства лежат на адресе, ключ к которому можно получить только нашим
кодом (или вручную через SLIP-0010 `m/44'/607'/0'/0'` в инструментах, которые
это умеют). Для «продукта, который не запирает деньги» это недопустимо.

## Целевая схема

### Новые кошельки

1. **Генерация.** Цикл: `bip39.generateMnemonic(256)` (24 слова, валидный BIP39)
   → принять, если `mnemonicValidate(words)` из `@ton/crypto` = true (TON-валидна
   без пароля). В среднем ~256–300 итераций. Каждая стоит 1 HMAC + PBKDF2 на 390
   итераций, в браузере это доли секунды. Показать спиннер «создаём кошелёк».
2. **TON.** `mnemonicToPrivateKey(words)` из `@ton/crypto`. Это ровно алгоритм
   Tonkeeper. Контракт оставляем V4R2 (Tonkeeper при импорте находит V4R2 с
   балансом). Переход на W5 — отдельное решение, не сейчас.
3. **Остальные сети — без изменений.** `bip39.mnemonicToSeed(те же 24 слова)` и
   текущие пути: ETH `m/44'/60'/0'/0/0`, BTC `m/84'/0'/0'/0/0`, SOL
   `m/44'/501'/0'/0'`, TRON `m/44'/195'/0'/0/0`. Фраза проходит проверку BIP39,
   поэтому MetaMask/Phantom/Trust её примут.
4. **Адрес TON** показывать в форме `UQ…` (non-bounceable). Адрес не меняется,
   меняется только отображение. Парсер (`Address.parse`) понимает обе формы.
5. **Схема сохраняется явно:** новый ключ localStorage
   `wallet_ton_scheme = 'ton-mnemonic-v4r2'`. Отсутствие ключа означает
   `'slip10-607-0-0'` (все текущие кошельки).

### Импорт (восстановление)

- Принимать 12 и 24 слова (сейчас onboarding жёстко требует 12).
- Если `mnemonicValidate(words)` = true (24 слова, TON-валидна), TON выводится по
  TON-стандарту, схема `ton-mnemonic-v4r2`.
- Иначе (любая 12-словная и почти любая «чужая» 24-словная BIP39) TON выводится
  по legacy SLIP-0010, схема `slip10-607-0-0`. Так существующий пользователь при
  восстановлении видит **свой прежний** TON-адрес, а не пустой новый.
- Опционально при импорте 24-словной TON-валидной фразы: посчитать и legacy-адрес,
  и при ненулевом балансе показать «найдены средства на старом адресе». Это
  защищает от потери, если такая фраза когда-то была импортирована по старой схеме.

### Что не меняется

Ключи по-прежнему выводятся и подписывают только в браузере; seed не пишется в
localStorage; хранятся только зашифрованные блобы. Серверная часть не участвует.

## Миграция существующих тестеров

Все текущие кошельки 12-словные, поэтому схема у них `slip10-607-0-0`.
Пере-деривация на месте **невозможна**: из 12-словной фразы нельзя получить
Tonkeeper-совместимый ключ. Варианты:

### Вариант A (рекомендуемый, если у тестеров есть средства): «Перенос на новый кошелёк»

1. **Обнаружение.** При загрузке кошелька: `wallet_ton_scheme` отсутствует →
   legacy. Показать в Security center карточку «TON в этом кошельке нельзя
   восстановить в Tonkeeper. Перенести на новый кошелёк?». Без давления, можно
   отложить.
2. **Новый кошелёк.** Генерация 24-словной dual-valid фразы → показ → обязательная
   проверка бэкапа (выборочные слова). Раньше, чем пользователь подтвердил бэкап,
   никаких переводов.
3. **Старые ключи не удаляются.** Текущие `wallet_*_enc` / `wallet_keystore`
   переименовываются в `legacy_wallet_*` (зашифрованы тем же паролем). Новые
   пишутся в `wallet_*`. Порядок записи: сначала новые блобы, readback-проверка,
   потом переключение активного кошелька. При сбое на любом шаге активным остаётся
   старый кошелёк.
4. **Перевод средств (sweep)** — поштучно по каждой сети, через существующий
   send-flow с review-симуляцией и явным подтверждением на каждый перевод
   (инвариант «никаких автоматических денежных действий»):
   - токены раньше нативной монеты (им нужен газ): USDT-TON → TON, USDT TRC-20 →
     TRX, USDT ERC-20 → ETH;
   - нативный остаток: сумма «баланс минус оценка комиссии» (MAX уже так считает).
     Для TON — send mode «весь остаток» (128) **без** флага уничтожения (32);
   - сети с нулевым балансом пропускаются.
5. **Состояние.** Машина состояний на сеть (`pending → sent → confirmed`)
   в localStorage, чтобы прерванный перенос продолжался, а не начинался заново
   (защита от двойных переводов).
6. **Хвост.** `legacy_wallet_*` остаются, пока пользователь сам не нажмёт
   «удалить старый кошелёк». Кнопка активна только при нулевых балансах старых
   адресов. До этого в UI есть read-only «старый кошелёк» с балансами.
7. **Аудит.** События `ton_migration_offered/started/chain_swept/completed` с
   trace id, без адресов и сумм (как в `tx-draft`).

### Вариант B (если у тестеров только пустые/тестовые кошельки): «новые — по-новому, старые — как есть»

- Новые кошельки создаются по новой схеме. Legacy-кошельки продолжают работать
  (импорт 12 слов выводит legacy TON).
- Для legacy в Security center — предупреждение: «TON этого кошелька
  восстанавливается только в NeuroWallet. Чтобы пользоваться Tonkeeper, создайте
  новый кошелёк и переведите средства». Без инструмента sweep.
- Это повторяет прецедент `LEGACY_DERIVATION_JUNE_USERS.md` (accept + document).

### Что НЕ делать

- Не пере-выводить TON молча для существующих пользователей: их средства исчезнут
  из вида.
- Не просить вторую отдельную фразу только для TON: две резервные копии —
  гарантированные потери.
- Не экспортировать приватный ключ в открытом виде как «способ миграции».

## Реализация и приёмка (после одобрения)

- `lib/crypto/wallet.ts`: `generateMnemonic()` → dual-valid 24 слова;
  `importWalletFromMnemonic()` выбирает TON-схему по `mnemonicValidate`;
  сохранять `wallet_ton_scheme`.
- `pages/onboarding.tsx`: показ и проверка 24 слов; импорт 12 или 24.
- `ton-tx.ts`: отображение `UQ…`.
- Флаг `NEXT_PUBLIC_TON_MNEMONIC_ENABLED` (по умолчанию OFF).
- Тесты:
  - известная TON-мнемоника → ожидаемый V4R2-адрес (эталон получить ручным
    импортом в Tonkeeper и зафиксировать в `derivation-vectors.test.ts`);
  - сгенерированные фразы проходят и `bip39.validateMnemonic`, и
    `mnemonicValidate`;
  - 12-словный импорт даёт прежний legacy TON-адрес (регрессия);
  - ETH/SOL/BTC/TRON для 24-словной фразы совпадают с эталонами MetaMask/Phantom.
- Ручная приёмка: фраза нового кошелька → импорт в Tonkeeper показывает тот же
  TON-адрес и баланс → импорт в MetaMask показывает тот же ETH-адрес.
- Оценка: новая схема + onboarding на 24 слова ~1,5–2 дня; вариант A (sweep и
  машина состояний) ещё ~3–4 дня; вариант B (баннер) ~0,5 дня.

## Что нужно решить

1. **Одобряешь целевую схему** (24-словная dual-valid фраза, TON по стандарту
   Tonkeeper, остальные сети без изменений)?
2. **Есть ли у текущих тестеров реальные средства на TON-адресах?** Если нет —
   вариант B, если да — вариант A.
3. **Отображение `UQ…`** вместо `EQ…` — ок?
4. Перед реализацией вручную проверить на актуальной версии Tonkeeper: импорт
   24-словной фразы находит V4R2-кошелёк, и Tonkeeper не требует W5.
